# Migrations

Schema changes are managed with **Alembic** in `backend/alembic/versions/`. The current
head is **`0007_job_heartbeat`**.

> The backend does **not** auto-migrate on startup in local/free-tier compose. Run:
> ```bash
> docker exec codesensei-backend alembic upgrade head
> ```

## History

| Revision | File | Adds |
| --- | --- | --- |

| `0002_users_and_ownership` | `0002_users_and_ownership.py` | `users` table; `repositories.owner_id` + `is_public`; uniqueness → `(owner_id, url, branch)` |

| `0006_active_job_unique` | `0006_active_job_unique.py` | Partial unique index `uq_active_job_per_repository` on `(repository_id, status)` WHERE status IN ('queued','running') |
| `0007_job_heartbeat` | `0007_job_heartbeat.py` | `analysis_jobs.heartbeat_at` TIMESTAMPTZ (reaper liveness) |

## Common commands

```bash
# Apply all migrations
docker exec codesensei-backend alembic upgrade head

# Show current revision
docker exec codesensei-backend alembic current

# Create a new migration (autogenerate from ORM diff)
docker exec codesensei-backend alembic revision --autogenerate -m "describe change"

# Roll back one
docker exec codesensei-backend alembic downgrade -1
```

## Conventions
- One logical change per revision; numbered `000N_short_name`.
- Enums (`repository_status`, `analysis_job_status`, `symbol_kind`, `dependency_kind`) are
  Postgres enum types created in `0001`.
- New columns are nullable or defaulted so deploys are backward-compatible (rolling-safe).
- Always review autogenerated migrations — Alembic can miss server defaults and partial
  indexes (the `0006` partial index was written by hand).
